### インクリメント・デクリメント（一時変数と評価順序）
- **核心となるルール**: 前置インクリメント（`++x`）や前置デクリメント（`--x`）は「式が評価される前」に変数の値を 1 増減し、その結果を式の値として返します。後置インクリメント（`x++`）や後置デクリメント（`x--`）は「式が評価された後」に変数の値を 1 増減し、「増減前の値」を式の値として返します。複数の演算子がある場合、Java では「演算子の優先順位」と「左から右への評価順序（多くの二項演算子）」に従って、どの値がいつ読み出され、いつ書き戻されるかが決まります。
- **なぜそうなるのか**: Java 言語仕様では、前置・後置演算子それぞれに「値を読み出すタイミング」と「変数に書き戻すタイミング」が定義されています。コンパイラはこれに従って、まず変数の現在値を一時的に保持し、その後に加算・減算と代入を行うバイトコードを生成します。評価順序が決まっていることで、マルチスレッドなどを除いた通常の式評価では、同じ式は常に同じ結果になるように設計されています。
- **直感的な例え・オリジナル例**: 貯金箱を例にします。`++x` は「コインを 1 枚入れてから、今いくら入っているかを見る」操作に相当します。一方 `x++` は「今いくら入っているかを先にメモしておき、その後でコインを 1 枚入れる」操作です。例えば次のコードでは:

```java
int x = 5;
int a = ++x;   // x は 6 になり、a も 6
int b = x++;   // ここで b には 6（増やす前の値）、その後 x は 7 になる
```

`a` に代入するときは「先に貯金箱に 1 枚入れてから残高を見る」、`b` に代入するときは「いったん残高を紙にメモし、その後で 1 枚入れる」という違いがあります。
- **初学者の陥りやすい罠**: 前置と後置の違いを「なんとなく」で覚え、`x = x++` や `x = x++ + ++x` のように、同じ変数を 1 つの式の中で何度もインクリメントしてしまうと、読み出しと書き戻しのタイミングが混乱しやすくなります。また、Java では式の評価順序は決まっていますが、他言語では未定義な場合もあるため、「他言語の感覚を Java にそのまま当てはめる」と誤解を生みやすいです。テストや実務では、読み手にとって分かりづらい複雑なインクリメント表現は避け、必要なら一時変数や複数行に分けて書くことが推奨されます。

### equals のオーバーライドとオーバーロード（シグネチャと null の扱い）
- **核心となるルール**: `Object` クラスの `equals` メソッドのシグネチャは `public boolean equals(Object obj)` です。クラスが「等価性の判定方法」を独自定義したい場合は、このシグネチャを保ったまま実装を上書きする（オーバーライドする）必要があります。引数型を変えて `boolean equals(MyClass other)` のように定義すると、それは別メソッドの追加（オーバーロード）であり、`Object` から継承された `equals(Object)` は依然としてそのまま残ります。また、`equals` の実装では、引数が `null` の場合や型が異なる場合にどう扱うかを明示的に定義することが重要です。
- **なぜそうなるのか**: Java の動的バインディングでは、実行時に実際のオブジェクトの型に基づいてメソッドが選択されますが、その対象となるのは「コンパイル時に決まっているメソッドシグネチャ」です。`Map` や `Set` など標準ライブラリは「`Object` 型の引数を取る `equals`」を前提に動作しているため、シグネチャが異なるメソッドは呼び出されません。`null` については、`null.equals(...)` のような呼び出しはコンパイル自体は通るものの、実行時に `NullPointerException` になるため、通常は「`null` 側から `equals` を呼ばず、非 null 側から `equals` を呼ぶ」か、「`Objects.equals(a, b)` を用いる」という方針が取られます。
- **直感的な例え・オリジナル例**: 郵便物の宛先を考えます。郵便局は「住所 + 氏名」という形式で宛先を解釈する前提で動いています。ここで、独自に「ニックネームだけで届く特別便」というルールを自宅の中だけで決めても、郵便局はその形式を知らないので使ってくれません。`equals(Object)` を正しくオーバーライドするのは、「郵便局が理解している標準フォーマットに沿って、自宅の住所情報を登録し直す」イメージです。`boolean equals(MyType other)` だけを増やすのは、自宅ルールを追加しているだけで、郵便局（標準 API）は依然として古い住所登録を使い続けます。

```java
class Person {
    private final String name;

    Person(String name) {
        this.name = name;
    }

    @Override                    // シグネチャは Object のまま
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof Person other)) return false;
        return name.equals(other.name);
    }

    @Override
    public int hashCode() {
        return name.hashCode();
    }
}
```

- **初学者の陥りやすい罠**: `boolean equals(MyClass other)` だけを実装して「equals を作った」と考えてしまい、`Set` や `Map` で期待通りに重複判定が行われないケースがあります。また、`equals` をオーバーライドする際に `hashCode` を対応させていないと、ハッシュベースのコレクションで一貫した動作が得られません。`null.equals(x)` のように `null` 側から呼び出してしまい `NullPointerException` になることも多いため、`Objects.equals(a, b)` を用いるなどして「`null` 安全な比較」を習慣づけると混乱を減らせます。

### ビット演算と論理演算の違い（& と &&）
- **核心となるルール**: `&` 演算子は「ビット単位 AND」と「ブール値の論理 AND」の両方に使われますが、ブール値に対して用いた場合でも「両辺を必ず評価」します。一方、`&&` はブール値専用の「条件付き論理 AND」であり、左辺が `false` の場合は右辺を評価しません（短絡評価）。ビット演算としての `&` は整数型の各ビットごとに AND を取り、結果も整数型になります。
- **なぜそうなるのか**: `&&` は条件分岐を効率良く、かつ副作用を制御しやすくするために導入された演算子です。例えば右辺にメソッド呼び出しがあり、それがコストの高い計算や副作用（状態変更・例外など）を伴う場合、左辺だけで結果が決まるなら右辺を評価しない方が安全かつ効率的です。ビット演算の `&` は、CPU 命令に近いレベルで「ビットごとの AND」を表現するためのもので、論理値への適用も「両方の値をはっきり評価してから結果を決める」という仕様になっています。
- **直感的な例え・オリジナル例**: 2 つのチェックを考えます。「雨が降っているか」と「傘を持っているか」です。`&&` は「まず雨が降っているかを見る。降っていなければ、傘の有無はそもそも調べない」という態度です。`&` は「雨の有無も傘の有無も、どちらも必ず調べてから、『両方とも満たされているか』を判定する」という態度です。

```java
boolean isRaining = false;
boolean result1 = isRaining && checkUmbrella(); // checkUmbrella() は呼ばれない
boolean result2 = isRaining &  checkUmbrella(); // checkUmbrella() は必ず呼ばれる
```

- **初学者の陥りやすい罠**: 条件分岐で `&` と `&&` を混同し、右辺で `null` チェックより先にメソッドを呼んでしまい `NullPointerException` を起こすケースがあります（`a != null && a.method()` のように、短絡評価を前提にした書き方がよく使われます）。また、整数に対して `&` を用いるビット演算は、結果がブール値ではなく整数になるため、ビットマスクの目的を理解していないと「なぜこの計算をしているのか」が不明瞭になりがちです。どの場面でビット演算が必要なのか、どの場面では論理演算だけでよいのかを区別して学ぶことが重要です。

### if 文の中カッコ省略（直後の 1 文だけが対象）
- **核心となるルール**: `if` 文の条件が真のときに実行されるのは、「`if (条件)` の直後に続く 1 文だけ」です。複数の文を `if` の対象にしたい場合は、必ず `{ ... }` でブロックを作る必要があります。中カッコを省略した場合、その次に書かれた 1 文だけが条件付き実行になり、それ以降の文は `if` とは無関係に常に実行されます。
- **なぜそうなるのか**: Java の構文規則では、`if (条件)` の後に来るのは「文（statement）」であり、その「文」として「ブロック（`{` から `}` まで）」も 1 文とみなされます。したがって、ブロックを書かなければ、最初の 1 文だけが `if` に対応する「本体」として扱われます。この仕様により、構文解析が単純になり、コンパイラが文の境界を明確に判断しやすくなっています。
- **直感的な例え・オリジナル例**: 「雨が降っていたら、洗濯物を取り込んで、窓も閉める」という指示を、口頭で曖昧に伝えたとします。「雨が降っていたら洗濯物を取り込んで、窓を閉めて」と言うと、聞き手によっては「窓を閉める」のも条件付きだと解釈しますが、文章としては曖昧です。プログラムでは、

```java
if (isRaining)
    bringLaundryIn();
    closeWindow();  // これは雨に関係なく必ず実行される
```

という形になると、「洗濯物を取り込む」のみが条件付きで、「窓を閉める」は常に実行されます。両方を条件付きにしたいなら、

```java
if (isRaining) {
    bringLaundryIn();
    closeWindow();
}
```

とブロックで囲む必要があります。
- **初学者の陥りやすい罠**: インデントに頼って「見た目上、複数行が `if` の中にあるように見える」コードを書き、実際の動作と自分の想定がずれることが多いです。特に `if ... else` と組み合わせた場合、`else` がどの `if` に対応しているかを誤解しやすくなります。また、将来行を追加するときに中カッコを付け忘れ、バグを埋め込みやすいので、スタイルガイドでは「`if` の本体が 1 文でも `{}` を付ける」ことが推奨されることが多いです。

### switch の型と case（long 不可、enum 可、case には定数のみ）
- **核心となるルール**: 伝統的な `switch` 文では、式に使える型は `byte` / `short` / `char` / `int` とそのラッパー型、`enum`、および `String` です（Java 17 時点）。`long` / `float` / `double` / `boolean` は `switch` の式として使用できません。`case` ラベルには「コンパイル時定数式」のみが書けます。すなわち、`final` かつコンパイル時に値が確定しているプリミティブや `String` などであり、実行時に初期化される変数やメソッド呼び出しの結果などは書けません。
- **なぜそうなるのか**: もともと `switch` 文は、整数値に対するジャンプテーブルや分岐最適化を想定して設計されており、「取りうる値が有限かつ事前に分かる」ことを前提にしています。`enum` や `String` が後から対応したのも、コンパイラが内部的に整数値にマッピングできるからです。一方で `long` や浮動小数点型は値の範囲が広く、また浮動小数点には丸め誤差もあるため、`switch` の構造と相性が良くありません。`case` にコンパイル時定数のみを許すのも、ジャンプテーブルなどの最適化と一貫した動作を保証するためです。
- **直感的な例え・オリジナル例**: 入口に「0〜9 番のロッカーが並んでいる靴箱」を考えます。`switch` は「この番号が来たらこのロッカーを開ける」という、あらかじめ決まった分岐に向いています。`enum` は「春・夏・秋・冬」のように、取りうる値が有限で名前付きの選択肢として整理されているイメージです。一方、「身長」や「体重」のようにほぼ連続的な値を `switch` で分けるのは現実的ではなく、`if` 文で範囲による条件分岐を行う方が自然です。

```java
enum Season { SPRING, SUMMER, AUTUMN, WINTER }

Season s = Season.SUMMER;
switch (s) {
    case SPRING -> System.out.println("花見の季節");
    case SUMMER -> System.out.println("海の季節");
    case AUTUMN -> System.out.println("紅葉の季節");
    case WINTER -> System.out.println("雪の季節");
}
```

- **初学者の陥りやすい罠**: `long` 型の値を直接 `switch` に渡そうとしてコンパイルエラーになることがあります（`incompatible types: possible lossy conversion` など）。また、`case` に書いたつもりの値が「コンパイル時定数」と見なされず、`case label is not a constant expression` というエラーになるケースも典型的です（例えば、`final` だがメソッド内で代入されている変数など）。`enum` を使う場合は、「`default` をどう扱うか」「将来列挙子が増えたときにどのように対応するか」を意識しておくと、保守性の高いコードになります。

### switch 式（網羅性と default の必要性）
- **核心となるルール**: Java 14 以降の `switch` 式（Java 17 では標準機能）では、`switch` 全体が値を返す式として扱われます。このため、すべての実行経路で値が決まるように「網羅性」が求められます。`enum` など取りうる値が限定されている型に対して、すべての列挙子を `case` で記述すれば `default` を省略できますが、そうでない場合は `default` を用いて「その他すべて」の場合に対する値も指定する必要があります。
- **なぜそうなるのか**: 通常の文としての `switch` は、「どの分岐が実行されなくてもコンパイル上は問題ない（何も起こらないだけ）」という性質を持ちますが、式としての `switch` は「必ず値を返す」ことが前提です。コンパイラは静的解析により、列挙型などについては「列挙子を全部列挙していれば網羅されている」と判断できますが、整数や `String` など値の範囲が広い型ではそれができないため、`default` によって残りのすべてのケースを代表させる必要があります。
- **直感的な例え・オリジナル例**: 「今日の気分」を 0,1,2 の 3 段階で入力してもらい、それに応じたメッセージを必ず返すアンケートシステムを考えます。どの値を入力されても、システムとしては「必ず何らかのメッセージを返す」必要があります。`switch` 式における網羅性は、「どのボタンを押されても案内メッセージを返すように、パネル側で事前に全パターンを潰しておく」ことに相当します。

```java
enum TrafficLight { RED, YELLOW, GREEN }

TrafficLight light = TrafficLight.RED;
String action = switch (light) {
    case RED    -> "止まる";
    case YELLOW -> "注意して準備";
    case GREEN  -> "進む";
    // enum の全要素を列挙しているので default は不要
};
```

- **初学者の陥りやすい罠**: 従来の `switch` 文と同じ感覚で `switch` 式を書き、ある分岐で値を返し忘れてコンパイルエラーになることがあります。また、「一部の `case` だけで値を返し、その他は何もしない」ような書き方は `switch` 式ではできないため、従来の `switch` 文と役割を混同しないことが重要です。さらに、`yield` を用いるブロック形式の `case`（複数文を含む場合）と、矢印（`->`）を用いる簡易形式の違いにも注意が必要です。

### for 文の初期化・条件（同じ型のみ、条件は 1 式のみ）
- **核心となるルール**: 通常の `for` 文は `for (初期化; 条件; 更新)` という構造をとり、`初期化` には 0 個以上の変数宣言や式をカンマ区切りで書けますが、変数宣言を複数書く場合は「同じ型」である必要があります。`条件` 部分には「ブール式を 1 つだけ」書けます。C 言語とは異なり、`for (i = 0, j = 0; i < n, j < m; ...)` のようにカンマで複数の条件を書く構文は存在せず、条件として評価されるのは 1 つの式だけです。
- **なぜそうなるのか**: Java の `for` 文は C 系言語の構文に似せつつも、「条件部は常にブール式である」という一貫性を重視して設計されています。複数条件をカンマで並べる構文は、C 言語においても読みづらさを生む傾向があり、Java では採用されていません。初期化部の複数宣言に型の制約を設けているのも、宣言文の構文を単純に保つためです。
- **直感的な例え・オリジナル例**: 授業の点呼をイメージします。「1 人目から順番に出欠を取る」という処理で、`for` 文は「点呼を開始する準備（初期化）」「まだ全員終わっていないかどうか（条件）」「次の生徒に進む（更新）」という 3 段階を 1 セットにします。条件は「全員終わったかどうか」という 1 つだけであり、「教室の温度が快適かどうか」など別の条件は、通常は点呼とは独立した場所で扱います。

```java
for (int i = 0, j = 10; i < j; i++, j--) {
    System.out.println(i + ", " + j);
}
```

- **初学者の陥りやすい罠**: C 言語の経験がある場合に、「条件部にもカンマを使って複数条件を書ける」と誤解しやすいです。また、初期化部で `int i = 0, long j = 0L;` のように異なる型を混在させようとしてコンパイルエラーになるケースもあります。条件を複雑にしすぎると読みづらくなるため、必要であれば条件式をメソッドに切り出す、あるいはループを分けるなどして意図を明確にすることが重要です。

### 拡張 for 文と参照（一時変数への代入は配列に影響しない）
- **核心となるルール**: 拡張 `for` 文（`for-each`）は、配列や `Iterable` の各要素を「一時変数に順番に代入」して処理します。この一時変数に新しいオブジェクトや値を代入し直しても、元の配列やコレクションの要素は書き換わりません。プリミティブ型の場合は「値のコピー」が渡され、参照型の場合も「参照のコピー」が一時変数に入り、その一時変数を別の参照で上書きしても、元のコンテナ内の参照は変わりません。
- **なぜそうなるのか**: 拡張 `for` 文は、内部的にはイテレータや添字を使ったループに変換されますが、各要素は「読み取り専用のスナップショット」として一時変数に渡されます。一時変数はローカル変数であり、その変数に対する代入はローカル変数自身を書き換えるだけで、コンテナ側の要素には影響しません。ただし、参照型の場合は「参照先のオブジェクトのフィールドを変更する」操作（`item.setX(...)` など）は、当然ながら元の要素にも反映されます。
- **直感的な例え・オリジナル例**: 本棚に並んだ本を 1 冊ずつ手に取って読む場面を想像します。拡張 `for` 文の一時変数は「今手に取っている本」を指しますが、その手に持っている本を途中で別の本と持ち替えても、本棚に並んでいる本自体は自動で入れ替わりません。本棚の本を入れ替えたければ、本棚から直接差し替える操作（添字を使った代入など）が必要です。

```java
int[] nums = {1, 2, 3};
for (int n : nums) {
    n = n * 10; // n は一時変数なので、配列 nums 自体は変わらない
}
// nums は依然として {1, 2, 3}
```

- **初学者の陥りやすい罠**: 拡張 `for` 文の一時変数に代入しても配列やリストの要素が変わると誤解し、「ループ後も元の配列が変わっているはず」と思い込むケースがあります。配列の中身そのものを変更したい場合は、通常の `for` 文で添字を用い、`array[i] = ...` のように直接代入する必要があります。また、参照型の場合に「一時変数を書き換えても元のコレクションは変わらないが、一時変数経由でオブジェクトの内部状態を変えると元にも反映される」という違いを区別できていないと、意図しない副作用を招くことがあります。

### do-while 文と等価な while 文（判定タイミングの違い）
- **核心となるルール**: `do-while` 文は「本体のブロックを少なくとも 1 回は実行してから条件判定を行う」構造を持ちます。これに対して通常の `while` 文は「最初に条件判定を行い、条件が真であれば本体を実行する」ため、条件が最初から偽の場合は本体が一度も実行されません。両者は「本体の実行回数の下限」が異なります。
- **なぜそうなるのか**: ユーザー入力のように「最低 1 回は必ず処理を行いたいが、その後は条件次第で繰り返したい」という場面を簡潔に表現するために、`do-while` が用意されています。コンパイラ視点では、`do-while` は内部的にラベル付きの `while` ループや `goto` に似た形に変換できますが、構文として分けることで「少なくとも 1 回は実行する」という意図を明示できます。
- **直感的な例え・オリジナル例**: 自販機で飲み物を買う場面を想像します。「1 回は必ずお金を入れてボタンを押す」操作をしてから、「もう 1 本買うかどうか」を考える流れは `do-while` に近いです。一方、「そもそもお金を持っているかどうかを先に確認し、持っていなければ何もしない」という流れは `while` に対応します。

```java
int count = 0;
do {
    System.out.println("一度は必ず表示される");
    count++;
} while (count < 0); // 条件は最初から偽だが、本体は 1 回実行される
```

- **初学者の陥りやすい罠**: `while` と `do-while` の違いを意識せずに書き換え、ループ本体が 0 回実行されるケースと 1 回実行されるケースを混同してしまうことがあります。また、`do-while` は末尾にセミコロンが必要（`while (条件);`）であり、ここを忘れて構文エラーや意図しない空文を作ってしまうこともあります。読み手にとって馴染みが薄いことも多いため、必要性が明確でない限り、通常は `while` で書き、どうしても「1 回は必ず実行」の表現が欲しい場合にだけ `do-while` を使うという方針もあります。

### 二重ループと break（外側の回数分だけ内側が実行される）
- **核心となるルール**: 二重ループでは、外側のループ 1 回ごとに内側のループが最初から最後まで（または途中で `break` されるまで）実行されます。内側の `break` はデフォルトでは「その内側ループ 1 層だけ」から抜けます。したがって、外側ループの回数 × 内側ループの回数（またはそれ以下）が、内側本体の実行回数のおおよその上限になります。
- **なぜそうなるのか**: ループは「何度も繰り返す処理の枠」であり、入れ子にすることで「ある単位ごとにさらに細かい処理を繰り返す」構造を表現します。`break` は、その「現在属している一番内側のループ」から抜けるキーワードとして定義されており、これにより制御構造が局所的に保たれます。外側のループまで一気に抜けたい場合は、ラベル付き `break` を用いるなど、より明示的な指定が必要です。
- **直感的な例え・オリジナル例**: 学校の時間割を考えます。外側ループが「曜日」、内側ループが「その日の各時限」に相当します。通常は「各曜日ごとに、1 限から順に授業を行う」ため、1 週間で「曜日の数 × 1 日の時限数」だけ授業が行われます。ある日の授業が全部終わったからといって、他の曜日まで自動的にスキップされるわけではありません。

```java
for (int day = 1; day <= 5; day++) {        // 外側ループ（曜日）
    for (int period = 1; period <= 6; period++) { // 内側ループ（時限）
        System.out.println(day + "日目 " + period + "時間目");
        if (period == 4) break; // その日の 4 限で授業終了（内側だけ抜ける）
    }
}
```

- **初学者の陥りやすい罠**: 「`break` したら二重ループ全体から抜ける」と誤解し、外側ループが継続していることに気づかないケースがあります。また、ループ変数の範囲や初期化の場所を誤り、意図より多く（または少なく）繰り返してしまうことも典型的です。二重ループの回数は、紙に小さな表を書いて「どの組み合わせが何回実行されるか」を手で追うことで理解しやすくなります。

### ラベルの付けられる場所（多くの文・ブロックに付けられる）
- **核心となるルール**: Java では、任意の文（`if` / `for` / `while` / `do-while` / `switch` / ブロック `{ ... }` など）に対して「ラベル名 + コロン」を先頭に付けることで、その文に名前（ラベル）を付けることができます。ラベルは主に、`break` や `continue` と組み合わせて「どのループやブロックに対して制御を移すか」を明示するために使われます。ラベル名は同じブロックスコープ内で一意である必要があります。
- **なぜそうなるのか**: ネストされたループやブロックが増えると、「どのループを抜けたいのか」「どのループをスキップしたいのか」を単純な `break` / `continue` だけでは表現しづらくなります。ラベル付きの制御文を導入することで、`break outer;` のように「外側の特定のループ」を直接指定できるようになり、構造化された `goto` のような役割を果たします。ただし、可読性を損なわないよう、乱用は避ける必要があります。
- **直感的な例え・オリジナル例**: ショッピングモールのフロア案内を想像します。各フロアに「1 階: 食品売り場」「2 階: 衣料品」などのラベルが付いており、「今いる場所から 1 階に戻る」といった指示を、ラベル名を使って表現できます。プログラムのラベルも同様に、複数の階層（ネスト）がある中で「どの階層に戻るか」を明示するための目印です。

```java
outer:
for (int i = 0; i < 3; i++) {
    inner:
    for (int j = 0; j < 3; j++) {
        if (i == j) {
            break outer; // outer ループから抜ける
        }
    }
}
```

- **初学者の陥りやすい罠**: ラベルは「`for` 文専用」だと誤解しがちですが、実際には多くの文やブロックに付けることができます。また、ラベル名を変数名と同様に扱ってしまい、同じスコープ内で重複した名前を付けてコンパイルエラーになることもあります。ラベル付き制御を多用するとコードの流れが追いづらくなるため、「どうしても外側まで一気に抜けたい特別な場合」に絞って使うのが現実的です。

### ラベル付き continue/break のトレース（どの i で内側が回り、何が加算されるか）
- **核心となるルール**: ラベル付きの `break` / `continue` は、「どのラベルが付いた文に対して適用するか」を明示します。`break ラベル;` は、そのラベルが付いた文から抜け出し、直後の文に制御を移します。`continue ラベル;` は、そのラベルが付いたループの「次の反復」の先頭に制御を移します。二重ループ以上で用いる場合、どのタイミングで内側ループが終了し、外側ループの次の反復に進むのかを、変数の値の変化と合わせて追う必要があります。
- **なぜそうなるのか**: 通常の `break` / `continue` では「一番内側のループ」にしか作用しないため、より外側のループの制御を直接変えたい場面では冗長なフラグ変数やネストの解除が必要になります。ラベル付きの構文は、こうした場面でコードを比較的簡潔に書くための仕組みです。制御フローが複雑になりやすいため、読み手が追いやすいように変数名やコメントで意図を補うことが多いです。
- **直感的な例え・オリジナル例**: エレベーターでの移動を考えます。通常の `break` は「今いる階層（ループ）だけから出る」のに対し、ラベル付き `break` は「指定した階層まで一気に戻る」ボタンのようなものです。ラベル付き `continue` は、「指定した階層の次の部屋に直接移動する」ようなイメージです。どの階でどのボタンを押したかを時系列で追うことで、移動経路（ループの実行順序）を理解できます。

```java
outer:
for (int i = 0; i < 3; i++) {
    for (int j = 0; j < 3; j++) {
        if (j == 1) continue outer; // outer の次の i へ
        System.out.println("i=" + i + ", j=" + j);
    }
}
```

- **初学者の陥りやすい罠**: ラベル付き `continue` と `break` の動きの違いを混同し、「どのループが何回回るか」を正しくイメージできないままコードを読むと、出力結果や変数の最終値を誤って予測しがちです。また、ラベルの位置（どの文に付いているか）によって挙動が変わるため、「ラベルの直後の文だけが対象」と誤解してしまうこともあります。二重ループ以上では、紙に `i` や `j` の値を追い書きしながらトレースすることで、制御の飛び先を正確に把握しやすくなります。
