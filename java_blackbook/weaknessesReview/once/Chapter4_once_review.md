### static フィールドはクラス名でアクセス可能でインスタンス不要
- 核心となるルール: `static` フィールドは「クラスに属する変数」であり、インスタンスではなくクラス自体に 1 つだけ存在する。そのため、コンパイラの推奨スタイルとしては `変数を宣言したクラス名.フィールド名` でアクセスできる。
- **なぜそうなるのか**: JVM のクラスロード時に、`static` フィールドは「クラスごとの領域（メタデータ領域＋静的領域）」に配置され、インスタンスごとのヒープ領域には含まれないため、インスタンス参照を介さずにクラス情報だけで読み書きできる。
- **直感的な例え・オリジナル例**: 会社ビル全体で共有する「非常口の場所マップ」のようなものを想像するとよい。社員（インスタンス）は何人いても、非常口マップ（`static` フィールド）はビル（クラス）に 1 枚だけあり、「社員Aのマップ」「社員Bのマップ」と個別に持つ必要はない。  
  ```java
  class Config {
      static String appName = "MyApp";
  }

  // 使用側
  String name = Config.appName;  // インスタンス不要
  ```
- **初学者の陥りやすい罠**:  
  - **インスタンスからもアクセスできてしまうため**、「インスタンスごとの値」と誤解しやすい（実際には全インスタンスで共有）。  
  - 同じクラスのインスタンスを複数作って `static` フィールドを変更すると「片方だけ変えたつもりが全員変わる」ことがある。  
  - 「`static` = グローバル」と短絡的に考えると、設計が崩れやすいので、「クラス全体で共有すべき性質のものか」を判断することが重要になる。

### static メソッドからアクセスできるのは static メンバだけ。非 static メソッドからは static にアクセス可
- **核心となるルール**: 静的メソッド（`static` メソッド）はクラスに属し、どのインスタンスにも結びつかないため、その本体から直接参照できるのは `static` メンバ（フィールド・メソッド）に限られる。一方、インスタンスメソッドは、クラス共有の `static` メンバにも、自身のインスタンスに属する非 `static` メンバにもアクセスできる。
- **なぜそうなるのか**: `static` メソッドが呼ばれるとき、JVM は特定のインスタンス参照（`this`）を持たない。非 `static` フィールドやメソッドは「どのインスタンスのものか」という `this` 情報がないと特定できないため、「直接アクセス不可」という制約になる。
- **直感的な例え・オリジナル例**:  
  ```java
  class Counter {
      static int totalCount = 0; // 全体の数
      int myCount = 0;           // 各人の数

      static void resetTotal() {
          totalCount = 0;
          // myCount = 0;   // どの人の myCount か分からないのでコンパイルエラー
      }

      void addOne() {
          myCount++;
          totalCount++;   // 全員共有の合計にはアクセスできる
      }
  }
  ```
- **初学者の陥りやすい罠**:  
  - `static` メソッド内で、暗黙に `this` を使っているような書き方（非 `static` フィールドへの直接アクセス）をしてコンパイルエラーになるケース。  
  - 「`static` メソッドからインスタンスメソッドを**絶対に**呼べない」と誤解することがあるが、**インスタンスを明示的に持っていれば** `instance.method()` の形で呼び出しは可能である（ただし、`this` を暗黙に使えないという意味）。

### 可変長引数は型の直後に ...
- **核心となるルール**: 可変長引数は「引数の型」の直後に `...` を付けて宣言し、メソッド定義の引数リストの中では**最大 1 つだけ**、かつ**最後の位置**に置く必要がある。
- **なぜそうなるのか**: コンパイラは可変長引数を「配列」で表現してバイトコードを生成するが、`...` の位置がばらばらだと「どこまでをその配列に束ねるか」を静的に決定できないため、構文規則として「型の直後」「最後の 1 個」に制約している。
- **直感的な例え・オリジナル例**:  
  ```java
  void printAll(String... words) {  // String の直後に ...
      for (String w : words) {
          System.out.println(w);
      }
  }

  // 呼び出し側
  printAll("apple", "banana", "cherry");
  printAll();  // 引数 0 個でもよい
  ```
  お店で「最後にまとめてお会計するカゴ」だと思うとよい。会計カゴ（可変長引数）はレジの一番最後にあり、それ以前のものは個別に処理される。
- **初学者の陥りやすい罠**:  
  - `String ... words` のように間にスペースを入れても構文上は許されるが、「型の直後」という感覚がぼやけやすい。  
  - 可変長引数を 2 つ以上並べる、途中に置く、といった宣言はコンパイルエラーになる。  
  - 「`String...` は `String[]` と全く別物」と思い込むこと。実際にはメソッド内部では `String[]` として扱われる。

### void の return; は有効。エラーになるのは return の後の到達不能コードの行
- **核心となるルール**: 戻り値型が `void` のメソッドでは、`return;` という形で「処理をそこで終了する」文を書くことができる。コンパイルエラーになるのは、「`return` 文があること」ではなく、「`return` の後に書かれた、到達不可能な文」が存在するとき。
- **なぜそうなるのか**: Java のコンパイラは「到達可能性解析」を行い、すべての実行経路でその文に制御が到達しないと静的に判断できる位置にあるコードを「到達不能コード」として扱う。この解析の結果、`return` の直後にある文は実行され得ないと判断され、仕様上コンパイルエラーとされる。
- **直感的な例え・オリジナル例**:  
  ```java
  void greet(boolean polite) {
      if (!polite) {
          System.out.println("No greeting.");
          return; // ここで処理終了はOK
          // System.out.println("ここはコンパイルエラー"); // 到達不能
      }
      System.out.println("Hello");
  }
  ```
  ドアを閉めて部屋を出たあとに「部屋の電気を消すスイッチを押すコード」を書いてしまうようなもの。既に部屋の外に出た（`return` した）ので、その後の操作は物理的に到達できない。
- **初学者の陥りやすい罠**:  
  - 「`void` メソッドでは `return` は書いてはいけない」と誤解すること。実際には早期終了のためによく使われる。  
  - `if (true) { return; }` のような明らかに終了するブロックの後に書いたコードがエラーになる理由が「文法」ではなく「到達可能性解析」によるものだと意識していない。

### あいまいなメソッド呼び出しのエラーは呼び出し元の行
- **核心となるルール**: オーバーロードされたメソッド群の中から、コンパイラが 1 つに特定できない「あいまいな呼び出し」がある場合、コンパイルエラーは**そのメソッドを呼び出している行**で報告される。
- **なぜそうなるのか**: コンパイラはメソッド定義ごとにバイトコードを生成する段階ではなく、「どのメソッドを呼び出すか解決しながら呼び出し式を解析する」段階であいまいさを検出する。そのため、エラーの責任範囲は「定義側」ではなく「呼び出し側」とみなされる。
- **直感的な例え・オリジナル例**:  
  ```java
  void process(int x) {}
  void process(long x) {}

  void use() {
      // process(1); // どちらにも変換できてあいまい、といったケースで呼び出し行がエラーになる
  }
  ```
  2 人の店員がいて、どちらに話しかけたのか分からないような呼びかけをしたとき、「どの店員にも明確に届いていない」責任は呼びかけた人側にある、というイメージ。
- **初学者の陥りやすい罠**:  
  - エラーがメソッド本体側に付くと想像してしまい、定義を探してしまうこと。実際には呼び出し式のある行を確認する必要がある。  
  - オーバーロードの解決ルール（より具体的なシグネチャを選ぶ、など）を十分理解していないと、「一見どれかに行けそうだが実はあいまい」という状態を見落としやすい。

### 初期化子はコンストラクタより先に実行
- **核心となるルール**: インスタンス生成時、インスタンス初期化子（`{ ... }` ブロック）とインスタンスフィールドの初期化は、コンストラクタ本体よりも前に実行される。`static` 初期化子（`static { ... }`）はクラスロード時に 1 回実行され、インスタンス生成とはタイミングが異なる。
- **なぜそうなるのか**: JVM はオブジェクトを生成するとき、「①フィールドのデフォルト値」「②フィールド初期化子とインスタンス初期化子」「③コンストラクタ本体」という順序でヒープ上のオブジェクト状態を構築するよう仕様で定めている。これにより、コンストラクタ実行時には「クラスで宣言された初期状態」が既に整っている。
- **直感的な例え・オリジナル例**:  
  ```java
  class Person {
      String name = "unknown";   // フィールド初期化
      {                          // インスタンス初期化子
          System.out.println("instance initializer");
      }
      Person(String name) {
          System.out.println("constructor");
          this.name = name;
      }
  }
  ```
  家を建てるとき、「骨組み（フィールド初期化・初期化子）」を先に組んでから、「内装のカスタマイズ（コンストラクタ）」をするイメージ。
- **初学者の陥りやすい罠**:  
  - インスタンス初期化子の存在を知らず、「なぜこのタイミングで実行されるのか」理解しづらい。  
  - 同じフィールドを初期化子とコンストラクタの両方で設定してしまい、どちらが最後の値を上書きするかを意識していない。

### 戻り値型があるとコンストラクタではなくメソッド。デフォルトコンストラクタは「1つもコンストラクタを定義していないとき」だけ追加
- **核心となるルール**: コンストラクタ宣言には戻り値型を書かない。クラス名と同じ名前であっても戻り値型（`void` 含む）が書かれていれば、それは通常のメソッドとして扱われる。また、ソースコードにコンストラクタが 1 つも定義されていない場合に限り、引数なしの「デフォルトコンストラクタ」が自動生成される。
- **なぜそうなるのか**: Java 言語仕様では「コンストラクタのシグネチャは『クラス名＋引数リスト』であり、戻り値型は持たない」と定義されている。戻り値型がある宣言は構文上「メソッド」と解釈される。また、自動生成されるデフォルトコンストラクタは「後方互換性」と「クラス定義の簡略化」のための仕様であり、明示的に 1 つでもコンストラクタを定義した場合には不要となるため生成されない。
- **直感的な例え・オリジナル例**:  
  ```java
  class Book {
      Book() { }         // これはコンストラクタ

      void Book() { }    // これは「Book という名前のメソッド」
  }
  ```
  「入居の手続き（コンストラクタ）」には『契約の結果（戻り値）』という概念がなく、ただ部屋を占有可能な状態にするだけ。一方、「問い合わせ電話（メソッド）」には質問と回答（戻り値）がある、と考えると区別しやすい。
- **初学者の陥りやすい罠**:  
  - `public void クラス名(...) {}` をコンストラクタだと思い込み、「なぜ意図したタイミングで呼ばれないのか」と混乱する。  
  - 引数付きコンストラクタだけを書いた結果、引数なしでインスタンス生成しようとしてコンパイルエラーになる（デフォルトコンストラクタが自動生成されなくなっている）。

### this(…) はコンストラクタの先頭でなければならない
- **核心となるルール**: 同一クラス内の別コンストラクタを呼び出す `this(...)` は、コンストラクタ本体内の**最初の文**でなければならない。`super(...)` も同様に最初の文ルールがあり、`this(...)` と `super(...)` を同じコンストラクタ内で両方書くことはできない。
- **なぜそうなるのか**: オブジェクトの初期化順序を一貫して管理するため、JVM は「コンストラクタ本体に入る前に、どのコンストラクタチェーンを経由するか」を決める必要がある。そのため、`this(...)`/`super(...)` を途中で呼び出すような構造を認めると、部分的に初期化された状態で再初期化される可能性が出てしまうため、仕様として禁止されている。
- **直感的な例え・オリジナル例**:  
  ```java
  class Point {
      int x, y;
      Point() {
          this(0, 0);  // 先頭ならOK
      }
      Point(int x, int y) {
          this.x = x;
          this.y = y;
      }
  }
  ```
  引っ越しのとき、「まずどの引っ越しプランにするか（`this(...)` で別コンストラクタを選ぶ）」を最初に決め、決めたプランに基づいて作業を進めるイメージ。途中で別プランに切り替えることは認めていない。
- **初学者の陥りやすい罠**:  
  - フィールド代入やログ出力を `this(...)` の前に書いてコンパイルエラーになる。  
  - `this(...)` と `super(...)` を両方書こうとしてエラーになり、「親クラスと自クラスの両方の初期化をしたいのに」と混乱する（実際には、`this(...)` でチェーンされた先のコンストラクタ内で `super(...)` を呼び出す構造にする）。

### 参照型を渡したときは同じインスタンスを指すため、メソッド内での変更が呼び出し元に反映される
- **核心となるルール**: Java ではメソッド呼び出し時に「引数の値」がコピーされて渡される。参照型変数の場合、コピーされるのは「参照値（どのオブジェクトを指しているか）」であり、メソッド内外の変数が**同じインスタンス**を指す。そのインスタンスの状態を変更すると、その変化は呼び出し元から見ても反映される。
- **なぜそうなるのか**: Java の引数渡しは「値渡し（pass-by-value）」のみだが、参照型の値は「オブジェクトへのアドレスに相当する参照」であるため、コピーを作っても指す先のオブジェクトは同一である。フィールド変更はヒープ上のオブジェクトに対する操作であり、参照を共有する全ての変数から観測できる。
- **直感的な例え・オリジナル例**:  
  ```java
  class Box { int value; }

  void fill(Box box) {
      box.value = 10;  // Box インスタンスの中身を変える
  }

  Box b = new Box();
  fill(b);
  System.out.println(b.value);  // 10 と出力される
  ```
  同じロッカーの鍵の「合鍵」を渡していると考えるとよい。鍵（参照）は複数あっても、ロッカー（インスタンス）は 1 個なので、中身を変えると全員に影響する。
- **初学者の陥りやすい罠**:  
  - 「Java は参照渡し」と説明されることがあるが、厳密には「参照の値渡し」である。メソッド内で引数変数に別のオブジェクトを代入しても、呼び出し元の変数が指す先は変わらない点を誤解しやすい。  
  - `List` などのコレクションを引数に渡し、メソッド内で要素を追加・削除すると呼び出し元にも影響することに気づかず、「なぜ勝手に変わったのか」と混乱する。

### コンパイルエラーになる問題では「どの表示か」より先に「コンパイルが通るか」を判断する
- **核心となるルール**: Java のコードを読むときは、まず「そのプログラムがコンパイル可能か（構文・型・到達可能性など）」を確認し、コンパイルに失敗する要因があれば、その時点で実行結果（表示内容など）を考える必要はない。
- **なぜそうなるのか**: Java はコンパイル時に多くのエラーを検出する静的型付け言語であり、コンパイルが成功しない限り JVM 上での実行には至らない。したがって、実行時の挙動を考える前に、コンパイル段階の検証が必須となる。
- **直感的な例え・オリジナル例**:  
  文法ミスだらけのレシピを見て「完成した料理の味」を議論しても意味がないのと同じで、まずはレシピとして成立しているか（材料名があるか、手順がつながっているか）を確認するイメージ。
- **初学者の陥りやすい罠**:  
  - 画面出力やロジックの流れだけに注目し、「そもそもコンパイルが通るのか」を見落とし、到達不能コードや型不一致などのエラーを後回しにしてしまう。  
  - IDE のエラーメッセージを無視して実行結果を想像しようとしてしまい、原因の特定が遅れる。

### レコードで宣言できないのは static でないフィールドの明示的追加
- **核心となるルール**: レコード（`record`）は「不変なデータキャリア」を表すクラス宣言の一形態であり、**コンポーネント（ヘッダに書かれたフィールド）以外のインスタンスフィールドを明示的に追加することはできない**。追加できるのは `static` フィールドや `static` メソッドなど、クラスレベルのメンバに限られる。
- **なぜそうなるのか**: レコードは、コンパイラがコンポーネントに対応するフィールドやアクセサなどを自動生成することを前提とした「透明なキャリア型」を意図しており、インスタンス状態がヘッダに完全に表現されていることが重要な設計方針である。追加のインスタンスフィールドを許すと、その透明性が損なわれるため、仕様として制約されている。
- **直感的な例え・オリジナル例**:  
  ```java
  public record User(String name, int age) {
      static int instanceCount;      // static はOK
      // int secret;                // インスタンスフィールドの追加はコンパイルエラー
  }
  ```
  レコードは「中身のラベルが全部表に印刷された透明な箱」で、箱の裏にこっそりもう一つのポケット（追加インスタンスフィールド）を付けることを禁止しているイメージ。
- **初学者の陥りやすい罠**:  
  - 従来のクラスと同じ感覚で「あとからインスタンスフィールドを足そう」としてコンパイルエラーになる。  
  - レコード内で `static` フィールドは許されることを忘れ、「レコードだからフィールド追加は全部ダメ」と極端に考えてしまう。

### トップレベルレコードの修飾子は public と修飾子なし
- **核心となるルール**: トップレベル（クラスの外側）に宣言されるレコードのアクセス修飾子として使用できるのは、`public` または修飾子なし（パッケージプライベート）のいずれかであり、`private` や `protected` は使えない。
- **なぜそうなるのか**: これは通常のトップレベルクラスと同じ規則であり、Java のアクセス制御モデルでは「モジュール／パッケージ単位で可視性を制御する」ことが基本となっている。トップレベルで `private` や `protected` を指定しても「外側に親クラスが存在しない」ため意味を持たないので、言語仕様として許可されていない。
- **直感的な例え・オリジナル例**:  
  ```java
  public record Point(int x, int y) {}  // OK
  record Line(Point start, Point end) {} // 修飾子なし（パッケージプライベート）

  // private record Hidden(int x) {}    // コンパイルエラー
  ```
  町の地図に載る建物（トップレベル宣言）は「公開されている（public）」か「その町の住人だけが知っている（パッケージプライベート）」かのどちらかであり、「家族にだけ見える建物（private）」という概念は成り立たないイメージ。
- **初学者の陥りやすい罠**:  
  - 通常のネストクラスと混同し、トップレベルに `private` や `protected` を付けようとしてしまう。  
  - 修飾子なしを「public」と誤解し、他のパッケージからアクセスできない理由が分からなくなる。

### 代替コンストラクタは標準と同じ引数か全フィールドの初期化が必要。static でないフィールドの追加は不可
- **核心となるルール**: レコードにおいては、コンパイラが生成する「正規コンストラクタ（ヘッダの全コンポーネントを引数に取るコンストラクタ）」に基づいて、独自のコンストラクタ（代替コンストラクタ）を定義する場合でも、**最終的に全てのコンポーネントが初期化されるようにする必要がある**。追加のインスタンスフィールドを持てないことも合わさり、「全コンポーネントを初期化しないコンストラクタ」は認められない。
- **なぜそうなるのか**: レコードの不変性と完全性（全コンポーネントが常に定義済みである状態）を保つため、JVM レベルでの表現も、ソースコードレベルの宣言も「コンポーネント = インスタンス状態の全部」という前提に立っている。コンストラクタのどの経路からインスタンスを生成しても、ヘッダに列挙された全てのフィールドが初期化されることをコンパイラが保証する必要がある。
- **直感的な例え・オリジナル例**:  
  ```java
  public record Range(int from, int to) {
      public Range(int value) {
          this(value, value);  // 最終的に from, to の両方を初期化
      }
  }
  ```
  レコードは「ラベル付きの欄が全部埋まった申込書」のようなもので、どの記入方法（コンストラクタ）を選んでも、最後には全ての欄が埋まっていなければ受理されないイメージ。
- **初学者の陥りやすい罠**:  
  - 一部のコンポーネントだけを初期化し、残りをデフォルト値に任せようとしてコンパイルエラーになる。  
  - 通常クラスの感覚で「後から別フィールドで補う」と考え、レコードの制約（追加インスタンスフィールド禁止）を忘れがち。

### コンパクトコンストラクタ内では this.フィールド は使えない
- **核心となるルール**: レコードのコンパクトコンストラクタ（`public レコード名(コンポーネント列) { ... }` の短縮形）では、コンポーネントは**まだフィールドに代入される前の「パラメータ」**として扱われる。そのため、コンストラクタ本体では `this.フィールド名` ではなく、単にパラメータ名で参照する形を用いる。
- **なぜそうなるのか**: コンパイラはコンパクトコンストラクタを展開して、（検証や再代入などを行ったうえで）最後に暗黙の代入 `this.field = fieldParam;` のようなバイトコードを生成する。コンストラクタ本体の中では、まだその暗黙の代入が行われていない段階と見なされるため、`this.フィールド` という形での参照を許可していない。
- **直感的な例え・オリジナル例**:  
  ```java
  public record Temperature(int celsius) {
      public Temperature {
          if (celsius < -273) {
              throw new IllegalArgumentException();
          }
          // this.celsius はまだ「フィールド」として代入前とみなされる
      }
  }
  ```
  申込書に書かれた値（パラメータ）を、まだシステムに登録していない状態と考えるとよい。審査（バリデーション）は申込書の値をそのまま見るのであり、「登録済みデータベースの値（`this.フィールド`）」を見る段階には達していない。
- **初学者の陥りやすい罠**:  
  - 通常クラスのコンストラクタと同じ感覚で、`this.フィールド名` を使おうとしてコンパイルエラーになる。  
  - コンパクトコンストラクタと「正規コンストラクタの明示定義」を混同し、それぞれのルール（暗黙の代入の有無）を取り違える。

### レコードの getter とインタフェースの default が同名で戻り値型が違うとコンパイルエラー
- **核心となるルール**: レコードのコンポーネント名に対応して自動生成されるアクセサメソッド（`コンポーネント名()`）と、インタフェースの `default` メソッドが同じシグネチャ（メソッド名・引数リスト）で、**戻り値型だけが異なる**場合、メソッド解決に矛盾が生じるためコンパイルエラーになる。
- **なぜそうなるのか**: Java のメソッドシグネチャは「メソッド名＋パラメータ型リスト」で決まると定義されており、戻り値型はシグネチャに含まれない。そのため、「同じシグネチャで戻り値型だけが異なる 2 つのメソッド」を 1 つのクラスに同居させることはできず、どちらを採用してももう片方と矛盾する。
- **直感的な例え・オリジナル例**:  
  ```java
  interface Named {
      default String name() { return "default"; }
  }

  public record User(String name) implements Named {
      // 自動生成される name(): String と default name(): String ならOK（オーバーライドになる）
      // 戻り値型が違う default name(): int などがあるとコンパイルエラー
  }
  ```
  getterメソッドが自動生成されるので、recordのコンポーネントにインタフェースのデフォルトメソッドとコンポーネントとデフォルトメソッドのメソッド名・引数は同じで、戻り値型だけ違う場合は、デフォルトメソッドと自動生成getterメソッドが名前衝突してしまう。
  戻り値型が同じなら衝突しない。
  コンポーネントに対応する自動生成メソッドと、インタフェースの default メソッドが 同じシグネチャ（名前＋引数） のとき、戻り値型が一致すればオーバーライドで問題なし。戻り値型が一致しないと、自動生成メソッドと default が両立できずコンパイルエラーになる。

  同じ電話番号（メソッドシグネチャ）に対して、1 つは「音声通話」、もう 1 つは「FAX」のみ、といった別サービスが同時に存在してしまうイメージで、どちらも同時には成り立たない。
- **初学者の陥りやすい罠**:  
  - 「戻り値型が違えば別メソッド」と思い込み、`int foo()` と `String foo()` を同じパラメータで並べようとしてコンパイルエラーになる。  
  - レコードの自動生成メソッドとインタフェースの `default` を意識せず、名前が衝突したときにどちらが採用されるかだけを考え、戻り値型の整合性を見落とす。

### 戻り値型が float のとき、受け取る変数は float と互換性のある型（double）の両方が正解になり得る
- **核心となるルール**: 戻り値型が `float` のメソッド呼び出し結果は、`float` 型の変数だけでなく、**より広い範囲を表現できる互換型である `double` 型の変数にも代入できる**（暗黙の拡大変換が行われる）。`double` から `float` への代入は縮小変換となり、明示的なキャストが必要になる。
- **なぜそうなるのか**: Java のプリミティブ型には「数値変換の拡大／縮小」の規則があり、`float` から `double` への変換は情報を失わない（または失わないとみなされる）拡大変換として自動的に許可されている。そのため、`double x = someFloatMethod();` のような代入は追加の記述なしでコンパイルされる。
- **直感的な例え・オリジナル例**:  
  ```java
  float f() { return 1.0f; }

  float a = f();   // 同じ型なのでそのまま代入
  double b = f();  // float → double へ自動拡大変換
  ```
  小さいコップ（`float`）に入っている水を、大きいボトル（`double`）に移すのは問題ないが、その逆（大きいボトルから小さいコップへ）はあふれる可能性があるので、明示的に「それでもよい」と宣言（キャスト）する必要があるイメージ。
- **初学者の陥りやすい罠**:  
  - 「メソッドの戻り値型と変数の型は**完全一致**でなければいけない」と思い込み、合法な拡大変換（`float` → `double` など）を見落とす。  
  - 自動変換の方向を逆に覚えてしまい、`double` から `float` への代入がコンパイルエラー（または警告ありのキャスト必須）になる理由が分からなくなる。
