### 配列・コレクションの範囲外アクセスと発生する例外
- **核心となるルール**: 配列でアクセスできるインデックスは`0`以上`length - 1`以下、`List`であれば`0`以上`size() - 1`以下、`String`であれば`0`以上`length() - 1`以下に限定されます。この範囲外のインデックスに対して要素参照や更新を行うと、配列では`ArrayIndexOutOfBoundsException`、`List`など一般的なコレクションでは`IndexOutOfBoundsException`、文字列では`StringIndexOutOfBoundsException`が実行時にスローされます。
- **なぜそうなるのか**: Javaの配列や`String`、`List`は、連続した要素領域を「先頭からのオフセット」で管理しており、JVMやライブラリは各アクセスのたびに「インデックスが0以上、要素数未満か」を検査します。範囲外であれば、そのままメモリを読みに行くと不正アクセスになるため、そこで処理を中断し、状況に応じた例外オブジェクト（配列なら`ArrayIndexOutOfBoundsException`など）を生成してスローする設計になっています。
- **直感的な例え・オリジナル例**: 5人掛けのベンチに「左から0〜4番の席」という番号を振って座らせるとします。6人目が来て「5番の席に座りたい」と言っても、その席は存在しないので案内係は「その席はありません」と対応を止めます。コードでは次のようなイメージです。

```java
int[] seats = new int[5]; // 有効インデックス: 0〜4
seats[5] = 1;             // 実行時に ArrayIndexOutOfBoundsException
```

- **初学者の陥りやすい罠**: 
  - **最大インデックスを`length`だと誤解する**: 「要素数が`length`なら、最大インデックスも`length`」と考えて`array[length]`にアクセスし、範囲外になるケースが多いです。常に「最大インデックスは`length - 1`／`size() - 1`」という関係を意識する必要があります。
  - **負のインデックスが使えると誤解する**: 他言語の癖で`-1`を末尾とみなしてしまいがちですが、Javaでは負のインデックスはすべて範囲外で、例外がスローされます。
  - **空の配列・空のリストの扱い**: 「配列やリスト変数がnullではない」ことと「中に要素が1つ以上ある」ことを混同し、長さ0にもかかわらずインデックス0を参照して例外を発生させることがあります。
  - **どの型でどの例外か混同する**: 配列＝`ArrayIndexOutOfBoundsException`、文字列＝`StringIndexOutOfBoundsException`、`List`など一般コレクション＝`IndexOutOfBoundsException`という対応関係を整理しておくと、スタックトレースから原因をたどりやすくなります。

### `main(String[] args)` と null／長さ0の違い
- **核心となるルール**: Javaアプリケーションの入り口である`main`メソッドは`public static void main(String[] args)`という形で定義され、コマンドライン引数が1つも指定されなかったときでも、`args`にはnullではなく「要素数0の`String`配列」が渡されます。そのため、`args.length`は常に0以上の整数であり、「配列変数がnullかどうか」と「配列の要素数が0かどうか」は別々に判定する必要があります。
- **なぜそうなるのか**: `main`を呼び出すのはJVMであり、起動時にコマンドライン引数を配列として構築してから`main`に渡す、という仕様になっています。引数が0個の場合は、要素を持たない`String[]`インスタンスが生成され、その参照が`args`に渡されます。このため、`args`自体がnullになる状況は通常の起動手順では想定されていません。
- **直感的な例え・オリジナル例**: 会議の出席者リストを紙で受け取るとします。参加者が0人でも、主催者は「空のリスト」を渡し、紙そのものが存在しない（null）状態にはしないと決めているイメージです。コードでは次のように区別します。

```java
public static void main(String[] args) {
    System.out.println(args == null);  // 通常の起動では false
    System.out.println(args.length);   // 引数0個なら 0
}
```

- **初学者の陥りやすい罠**: 
  - **「引数がない＝argsがnull」と思い込む**: 実際には`args`は空配列なので、`if (args == null) { ... }`という分岐は通常意味を持ちません。チェックすべきなのは`args.length == 0`かどうかです。
  - **nullと長さ0を混同する**: 「配列変数がnullである」ことは「配列オブジェクトそのものが存在しない」状態であり、「長さ0」は「配列は存在するが中身が1つもない」状態です。この2つを区別しないと、`args.length`を呼ぶ前のnullチェックの要否などを誤りがちです。

### try-catch-finally の構文ルールと実行順序
- **核心となるルール**: 文法として許される並びは、`try { ... } catch(...) { ... } finally { ... }`と`try { ... } finally { ... }`の2パターンに限られます。`catch`節は0個以上、`finally`節は0または1個で、`finally`は必ず`catch`の後ろにのみ書けます。`try`や`catch`の中で`return`や例外スローがあっても、呼び出し元に制御が戻る前に`finally`ブロックが実行されるように設計されています。
- **なぜそうなるのか**: `try`構文の目的は「例外発生の有無にかかわらず、後始末を確実に行う」ことにあります。そのため、JVMは`try`ブロックや`catch`ブロックで`return`や例外スローが発生した場合でも、いったん「戻り値やスローする例外を一時的に保持し、先に`finally`を実行してから制御を終了する」という手順で処理を進めます。構文ルールが限定されているのは、この制御フローを単純かつ予測しやすく保つためです。
- **直感的な例え・オリジナル例**: 部屋を出るときに「ドアを閉める」という作業を必ず実行したい状況を考えます。途中で話が終わっても、急に用事ができて走って出ても、「最後にドアを閉める」作業だけは必ず行う決まりを`finally`に相当すると捉えられます。

```java
static int sample() {
    try {
        return 1;
    } catch (RuntimeException e) {
        return 2;
    } finally {
        System.out.println("必ず実行される");
    }
}
```

- **初学者の陥りやすい罠**: 
  - **`try`だけ単独では書けない**: `try { ... }`の後には、必ず`catch`か`finally`のどちらか（または両方）が必要です。どちらも書かないとコンパイルエラーになります。
  - **`finally`を複数書こうとする**: `finally`は1つまでであり、「複数の後始末を複数の`finally`に分ける」といった構文はありません。
  - **`finally`内での`return`や代入の影響を誤解する**: `finally`の`return`は、`try`や`catch`で決まっていた戻り値・例外を上書きすることがありますが、プリミティブ値などをローカル変数にコピーした後であれば、そのコピー自体は変わらないといった振る舞いに注意が必要です。
  - **ネスト時の実行順序を混同する**: 内側の`try-catch-finally`がすべて処理されてから、外側の`finally`が実行される、という「内側→外側」の順番を意識しておく必要があります。

### catch の並び順と到達不能コード
- **核心となるルール**: 例外クラスには継承関係があり、サブクラス型の例外はスーパークラス型の`catch`節でも捕捉できます。このため、`catch`節を並べるときに、より広い型（スーパークラス）を先に書いてしまうと、その後ろにある狭い型（サブクラス）の`catch`は「到達不能」と判断され、コンパイルエラーになります。`catch`は「サブクラス → スーパークラス」の順で並べるのが基本です。
- **なぜそうなるのか**: コンパイラは、上から順に`catch`節を評価すると仮定して到達性を解析します。スーパークラス型の`catch`でサブクラスの例外も含めて捕捉できる場合、後続のサブクラス型`catch`はどの例外でも通らないと判定されるため、「決して実行されないコード」とみなされてエラーとなります。
- **直感的な例え・オリジナル例**: 「動物全員集合」という集まりで、入り口に「犬だけ入れる」「哺乳類なら入れる」という2つの受付があるとします。先に「哺乳類なら入れる」受付を通してしまうと、犬はすべてそちらで処理されるため、後ろに「犬だけ入れる」受付を置いても誰も来ません。これが到達不能`catch`に相当します。

```java
try {
    // 何らかの処理
} catch (IOException e) {
    // ここで IOException を処理
} catch (Exception e) {  // Exception は IOException のスーパークラス
    // ここでそれ以外の例外を処理
}
```

- **初学者の陥りやすい罠**: 
  - **「汎用的なExceptionから書く」と覚えてしまう**: 「とりあえず`Exception`を先にcatchする」という書き方は、その後に続く個別例外の`catch`をすべて到達不能にしてしまいます。
  - **継承関係を意識せずに並べる**: どの例外がどのスーパークラスを持つかを確認せずにcatch順序を決めると、コンパイルエラーや意図しない捕捉順序につながります。

### チェック例外・非チェック例外・Error の違い
- **核心となるルール**: `Exception`のうち`RuntimeException`とそのサブクラス以外は「チェック例外」と呼ばれ、発生可能性のあるメソッドでは、`try-catch`で処理するか、`throws`句で宣言することが求められます。`RuntimeException`系は「非チェック例外」であり、`throws`に書くことはできますが必須ではありません。`Error`やそのサブクラス（`StackOverflowError`など）は、通常のアプリケーションコードで回復を試みる対象とは想定されておらず、`catch`や`throws`の義務はありません。
- **なぜそうなるのか**: チェック例外は「呼び出し側での対処が期待される異常状態」を表し、コンパイラレベルで「対処の明示」を強制するための仕組みです。非チェック例外は、主にプログラミングミス（null参照や不正なキャストなど）を表し、コード修正で防ぐことが前提のため、宣言義務がありません。`Error`はJVMや実行環境レベルの深刻な問題を表し、通常のアプリケーションでの回復は困難と想定されるため、例外処理の対象外とされています。
- **直感的な例え・オリジナル例**: 日常のトラブルを「事前に申請が必要なもの」と「突然発生するもの」に分けるイメージです。飛行機の欠航のように「起こりうることがあらかじめ知られていて、対応手順も決まっている」ものがチェック例外、うっかり財布を忘れるような「本来起こしてはいけない不注意」が非チェック例外、地震など「アプリケーションレベルでコントロールしにくい事象」が`Error`に対応すると捉えられます。

```java
void readFile() throws IOException {   // チェック例外をthrowsで明示
    // ...
}

void parseInt(String s) {              // 非チェック例外はthrows不要
    Integer.parseInt(s);              // NumberFormatException が起こりうる
}
```

- **初学者の陥りやすい罠**: 
  - **すべての例外を`throws`で投げればよいと考える**: チェック例外を`throws`に積み上げるだけでは、結局どこかで必ず対処が必要になります。どの層で処理すべきかの設計も重要です。
  - **`RuntimeException`も必ず捕捉しようとする**: 非チェック例外は、基本的にはプログラムのバグを直すことで防ぐべきものであり、むやみにcatchして握りつぶすと問題の発見が遅れます。
  - **`Error`を通常の例外と同列に扱う**: `StackOverflowError`などをcatchして続行しようとするコードは、かえってシステムを不安定にすることがあります。

### null とメソッド呼び出し
- **核心となるルール**: 参照型変数が`null`のときに、その変数を通じてインスタンスメソッドやフィールドにアクセスしようとすると、実行時に`NullPointerException`がスローされます。`""`（長さ0の空文字）や`Collections.emptyList()`のような「中身が空のオブジェクト」と`null`はまったく別物であり、`null`にはそもそもインスタンスが存在しない点が重要です。
- **なぜそうなるのか**: メソッド呼び出しやフィールド参照では、JVMはまず「対象オブジェクトの参照」を使って実際のインスタンスをメモリ上で特定しようとします。参照が`null`の場合、そのインスタンスを特定することができないため、そこで処理を中断し`NullPointerException`をスローするようになっています。
- **直感的な例え・オリジナル例**: リモコンでテレビのチャンネルを変えることを考えます。手にリモコン（オブジェクト参照）があればボタンを押せますが、そもそもリモコンを持っていない状態（null）でボタンを押そうとすると、「ボタンを押す対象そのものが存在しない」ため操作は不可能です。

```java
String text = null;
int len = text.length();  // 実行時に NullPointerException
```

- **初学者の陥りやすい罠**: 
  - **空文字とnullの混同**: `""`は長さ0の`String`インスタンスであり、`"".length()`は0を返しますが、`null.length()`は`NullPointerException`になります。「存在するが中身が空」と「存在しない」の違いを意識する必要があります。
  - **`null.equals(...)`を呼んでしまう**: 比較対象が`null`である可能性がある場合は、`"OK".equals(str)`のように「絶対にnullにならない側」から`equals`を呼ぶパターンが安全です。
  - **nullチェックを忘れる**: ライブラリメソッドの戻り値がnullを許容するかどうかのドキュメントを確認せずに、そのままメソッド呼び出しを続けてしまうと、意図しない`NullPointerException`につながります。

### キャストと ClassCastException
- **核心となるルール**: ある参照を別の型にキャストする場合、その実体オブジェクトがキャスト先の型（またはそのサブタイプ）でなければ、実行時に`ClassCastException`がスローされます。コンパイル時に継承関係やインターフェース実装関係が存在していればキャスト自体は許可されますが、実行時の実体が対応していないときに例外が発生します。
- **なぜそうなるのか**: コンパイル時には「型の組み合わせが理論上ありうるか」までしか検査できません。実際にどのクラスのインスタンスが入っているかは、実行時の代入経路によって決まります。JVMはキャスト時にオブジェクトの実際の型情報を参照し、「キャスト先型と互換性があるか」を確認し、互換性がなければ`ClassCastException`をスローします。
- **直感的な例え・オリジナル例**: 「乗り物」という共通カードがあって、その中に実際には自転車のチケットが入っている状況を考えます。このカードを「電車専用のカード」と見なして改札に通そうとしても、中身が自転車のチケットなのではねられます。これが実行時の`ClassCastException`に相当します。

```java
Object obj = "text";
Integer n = (Integer) obj;  // 実行時に ClassCastException
```

- **初学者の陥りやすい罠**: 
  - **継承・実装関係のない型へのキャスト**: コンパイルは通るが、実行時に`ClassCastException`が出る典型例です。実体の型とキャスト先の型の関係を意識する必要があります。
  - **`equals`実装で`instanceof`を省略する**: 引数が自分のクラスであることを確認せずにいきなりキャストすると、他クラスのインスタンスが来たときに`ClassCastException`が発生します。`if (!(obj instanceof MyClass)) { return false; }`のような型チェック→キャスト→比較というパターンが定石です。
  - **ジェネリクスの型安全性を過信する**: 生の型（raw type）や無警告キャストを多用すると、コンパイル警告を無視した結果として実行時の`ClassCastException`に悩まされることがあります。

### マルチキャッチと継承関係の制約
- **核心となるルール**: マルチキャッチ構文`catch (A | B e)`では、`A`と`B`の型同士が継承関係にあってはいけません。片方の型がもう一方のサブクラス（またはスーパークラス）である場合、その2つを同じマルチキャッチに並べるとコンパイルエラーになります。一方、`IOException`と`RuntimeException`のように共通のスーパークラスは持つが直接の継承関係にない型同士は、同じマルチキャッチに並べることができます。
- **なぜそうなるのか**: マルチキャッチでは、キャッチ変数`e`の静的型は「列挙した型のうちもっとも共通するスーパークラス」に近いものになります。型同士が継承関係にあると、広い方の型だけで十分に表現できるため、わざわざ両方を並べる意味がなくなり、読解性も落ちます。そのため、コンパイラは「継承関係にある型の組み合わせ」は不正として扱います。
- **直感的な例え・オリジナル例**: 入り口で「犬と動物を受け入れる」という2種類の札を1枚のボードに同時に書く状況を考えます。「動物」と書けば犬も含まれるので、「犬｜動物」と並べて書く意味はありません。一方、「犬｜鳥」のように互いに別系統であれば、1枚のボードに並べて書く意味があります。

```java
try {
    // 何らかの処理
} catch (IOException | RuntimeException e) { // これはOK（継承関係がない）
    // ...
}
```

- **初学者の陥りやすい罠**: 
  - **`catch (Exception | RuntimeException e)`を書こうとする**: `RuntimeException`は`Exception`のサブクラスなので、この組み合わせはコンパイルエラーになります。「マルチキャッチの型同士は継承関係NG」という一文で覚えておくと整理しやすいです。
  - **共通のスーパークラスを意識しない**: マルチキャッチで列挙する型を増やしすぎると、実際には共通の抽象的な型1つで十分である場合でも冗長なコードになりがちです。

### try-with-resources の仕様
- **核心となるルール**: try-with-resources構文`try (Resource r = ...) { ... }`では、`catch`や`finally`がなくてもコンパイル可能であり、`try`ブロックの終了時にリソースの`close()`が自動的に呼び出されます。`try`の丸括弧内に宣言できるのは`AutoCloseable`または`Closeable`を実装した型に限られ、そこで宣言した変数は「finalまたは実質的final」である必要があります。また、複数のリソースを並べた場合、`close()`の呼び出し順は宣言順の逆（最後に宣言したものから先）になります。
- **なぜそうなるのか**: リソースの開放忘れを防ぐために、JVMは`try`ブロックの終了時に自動で`close()`を呼び出すコードをコンパイル時に埋め込みます。変数が再代入可能だと「どのインスタンスに対して`close()`すべきか」が不明確になるため、finalまたは実質的finalに制限されています。複数リソースの`close()`順を宣言順の逆にしているのは、ネストした利用状況（たとえば外側のストリームが内側のストリームをラップしている場合）で、内側から順に安全に閉じられるようにするためです。
- **直感的な例え・オリジナル例**: コップを重ねて使う状況を考えます。小さいコップを大きいコップの中に入れて2つ重ねた場合、片付けるときは内側（最後に載せたコップ）から先に洗うほうが自然です。try-with-resourcesがリソースを「逆順でcloseする」のは、これに近いイメージです。

```java
try (java.io.BufferedReader reader =
         new java.io.BufferedReader(new java.io.FileReader("data.txt"))) {
    String line = reader.readLine();
    // 読み取り処理
} // ここで自動的に reader.close() が呼ばれる（例外の有無にかかわらず）
```

- **初学者の陥りやすい罠**: 
  - **`AutoCloseable`を実装していない型を括弧内に書く**: 単なる`Object`や`String`など、`close()`を持たない型をtry-with-resourcesの宣言部に書くとコンパイルエラーになります。
  - **リソース変数に再代入しようとする**: 括弧内で宣言した変数を`try`ブロック内で別のインスタンスに代入しようとすると、「実質的finalではない」とみなされてコンパイルエラーになります。
  - **`try`本体と`close()`の両方で例外が出たときの挙動を誤解する**: `try`本体で発生した例外がメインの例外としてスローされ、`close()`中の例外は「抑制された例外」として記録されます。スタックトレースで`getSuppressed()`を確認しないと見落とすことがあります。
  - **catch／finallyの実行順を混同する**: 例外なしの場合は「try本体 → リソースclose → finally」、例外ありの場合は「try本体で例外発生 → リソースclose → catch → finally」という順で進む点を整理しておく必要があります。
