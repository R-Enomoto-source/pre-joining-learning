### child.super.name の記述とコンパイル可否

ユーザー: @pre-joining-learning/java_blackbook/local_problems/questions/Chapter5_questions.md:523-546 
child.super.name = "sample";
だったら、sampleと表示されていましたか？

アシスタント:
いいえ。**`child.super.name = "sample"` という書き方は Java では使えず、コンパイルエラーになります。**

理由は次のとおりです。

1. **`super` は「そのクラスの中」でしか使えない**  
   `super` はサブクラスの中から「親クラスのメンバー」を参照するためのキーワードです。  
   クラスの外から「あるオブジェクトの親部分」を `child.super` のように参照する文法は Java にありません。

2. **`super` は「変数」ではない**  
   `super` はインスタンスのプロパティではなく、コンパイラが特別に解釈するキーワードなので、`child.super` のように「オブジェクト.super」と書くことはできません。

そのため、

- **`child.super.name = "sample"` を Main クラスに書いた場合**  
  → コンパイルエラーになり、実行はできません。  
  → したがって「sample と表示されるか？」という質問には「そのコードはコンパイルできないので、表示の話にはならない」が答えになります。

もし「Child クラスの中」で親の `name` をセットしたい場合は、Child のコンストラクタやメソッド内で、次のように書く必要があります。

```java
super.name = "sample";  // これは Child クラス内でのみ有効
```

このように Child 内で `super.name = "sample"` を実行したうえで、同じ Child インスタンスに対して `getName()` を呼べば、親の `name` が "sample" になっているので、`getName()` は "sample" を返し、表示も "sample" になります。

### フィールドのシャドウイングとメソッドのオーバーライド（可読性）

ユーザー: 可読性などを考えると基本的にはオーバーライドした方が良いですよね？

アシスタント:
はい。可読性と「意図どおりの動き」を考えると、**オーバーライドした方がよい**です。

この問題のコードでは:

- **Child** が自分用の `name` を持っている（親の `name` を隠している）
- でも **getName()** は親のままなので、親の `name`（`null`）が返る  
→ 「Child の name をセットしたのに、表示は null」という分かりにくい挙動になる

こういう「フィールドのシャドウイング」だけにしておくと:

- どの `name` が使われているか読み手に伝わりにくい
- ポリモーフィズムの期待（子インスタンスなら子の名前が返る）と違う

なので、**Child で getName() をオーバーライドする**のがおすすめです。

```java
public class Child extends Parent {
    String name;

    @Override
    String getName() {
        return this.name;  // 子の name を返す
    }
}
```

こうすると:

- 「子インスタンスなら子の name が返る」という意図がはっきりする
- 呼び出し側は `child.getName()` だけで一貫した振る舞いになる
- フィールドのシャドウイングに依存せず、メソッドのオーバーライドで「見え方」を制御できる

**まとめ:** 子クラスで同名フィールドを持たせるなら、そのフィールドを返す getter も子でオーバーライドしておく方が、可読性も保守性も良くなります。

### @Override を付けるべきか（オーバーライドしたメソッドすべて）

ユーザー: Javaの@Overideはすべてのオーバライドしたメソッドにつけるべきなのでしょうか​

アシスタント:
**はい。オーバーライドしたメソッドには、基本的にすべて `@Override` をつけるのがおすすめです。**

#### 理由

1. **コンパイル時にミスを検出できる**  
   `@Override` をつけると、「親クラス／インターフェースのメソッドを本当にオーバーライドしているか」をコンパイラがチェックします。  
   メソッド名の typo や、引数リストの変更で「オーバーライド」ではなくなった場合に、**コンパイルエラー**で教えてくれます。  
   つけないと、気づかずに「別の新規メソッド」として定義してしまうことがあります。

2. **意図が読み取りやすい**  
   そのメソッドが「親やインターフェースのメソッドの実装／上書き」であることが一目で分かります。

3. **インターフェースの実装メソッドにも有効**  
   インターフェースのメソッドを実装するときも `@Override` をつけられます（Java 6 以降）。同じ理由で、実装メソッドにも付けておくと安全です。

#### まとめ

- **必須ではない**が、**オーバーライド／実装したメソッドにはすべて付ける**習慣にすると、バグ防止と可読性の両方に役立ちます。  
- 逆に、オーバーライドでも実装でもないメソッドに `@Override` をつけるとコンパイルエラーになるので、「本当に上書き／実装しているメソッドだけ」に付ける、という意味でも分かりやすいです。

### インターフェースの private メソッドで共通処理をまとめる意味

ユーザー: デフォル トメソッ ドをよ り簡潔にする目的で、インタフェースにprivateメ
ソッ ドを追加することができます。これにより、複数のデフォル トメソッ ド
内で同 じ処理をしていた場合、その処理をまとめることでコー ドをより簡潔
に記述できるようにな ります。
どういうことでしょうか？
複数のデフォル トメソッ ド
内で同 じ処理をしていた場合、その処理をまとめるというのはどういうことでしょうか？
重複する処理であればデフォルトメソッドにまとめて処理を書くこともできると思います。

アシスタント:
「重複する処理はデフォルトメソッドにまとめればいいのでは？」という疑問に対する答えは、

**「まとめることはできるが、それだと“まとめた処理”がインターフェースの公開API（デフォルトメソッド）として外に見えてしまう。privateメソッドにすれば、同じように“まとめる”ことができるうえに、その処理はインターフェース内部の実装詳細として隠せる」**

ということです。

#### デフォルトメソッドだけでまとめた場合

共通処理を「別のデフォルトメソッド」にまとめることはできます。

```java
public interface Example {
    default void methodA() {
        commonLogic();  // 共通処理を呼ぶ
    }
    default void methodB() {
        commonLogic();
    }
    // 共通処理を「デフォルトメソッド」として定義
    default void commonLogic() {
        // 重複していた処理
    }
}
```

このとき `commonLogic()` は**インターフェースの一部**なので、

- 実装クラスから `commonLogic()` を呼べてしまう
- 「これは内部用のヘルパー」という意図が伝わりにくい
- インターフェースの「契約」としてのメソッドが増えてしまう

というデメリットがあります。

#### privateメソッドでまとめた場合（Java 9以降）

共通処理を**privateメソッド**にすると、「同じようにまとめる」ことができるうえに、その処理は**インターフェースの外には見えません**。

```java
public interface Example {
    default void methodA() {
        doCommonLogic();
    }
    default void methodB() {
        doCommonLogic();
    }
    // 共通処理は private → このインターフェースの default の中からだけ使える
    private void doCommonLogic() {
        // 重複していた処理
    }
}
```

- `doCommonLogic()` は **defaultメソッド同士の「中でだけ」使うヘルパー**として使える
- 実装クラスからは呼べない（APIに含まれない）
- 「重複をまとめた」という目的は同じで、**まとめ方をより適切にできる**

#### まとめ

- **「複数のデフォルトメソッド内で同じ処理をしていた場合、その処理をまとめる」**  
  → 共通部分を一か所に寄せる、という意味です。
- **「デフォルトメソッドにまとめることもできる」**  
  → その通りですが、それだと「まとめた処理」がデフォルトメソッドとして外に露出してしまいます。
- **「privateメソッドでまとめる」**  
  → 同じ「まとめる」ができるうえに、その処理を**内部実装として隠せる**ので、インターフェースを簡潔かつ意図どおりに保てる、という説明になっています。

つまり、「まとめる」こと自体はデフォルトメソッドでもできますが、**まとめた先を private にできる**のが、インターフェースに private メソッドを追加する目的、という理解でよいです。

### デフォルトメソッドを共通化したときの3つのデメリット（初学者向け）

ユーザー: それぞれ初学者にも分かりやすく正確に教えてください
実装クラスから commonLogic() を呼べてしまう
「これは内部用のヘルパー」という意図が伝わりにくい
インターフェースの「契約」としてのメソッドが増えてしま

アシスタント:
それぞれ、初学者向けに整理して説明します。

#### 1. 「実装クラスから commonLogic() を呼べてしまう」とは

**インターフェースで宣言したメソッドは、そのインターフェースを実装したクラスから「全部」使える**、というルールがあります。

- デフォルトメソッドで `commonLogic()` を用意すると、それは「インターフェースが提供するメソッドの1つ」になる  
→ 実装クラス側から `commonLogic()` を呼ぶことが**文法上・仕様上は正しい**ことになります。

```java
// インターフェース
public interface Example {
    default void methodA() { commonLogic(); }
    default void methodB() { commonLogic(); }
    default void commonLogic() { /* 共通処理 */ }  // デフォルトメソッド = 公開されている
}

// 実装クラス
public class MyClass implements Example {
    public void doSomething() {
        commonLogic();  // ← コンパイルも通るし、仕様上も「呼んでよい」ことになる
    }
}
```

- 本来は「methodA / methodB の内部でだけ使う共通処理」にしたいのに、  
  **実装クラスの開発者が commonLogic() を直接呼んでしまう**可能性がある、という意味です。
- 「実装クラスから commonLogic() を呼べてしまう」＝  
  **「内部用」にしたかったのに、外からも普通に呼べる状態になってしまう**、というニュアンスです。

#### 2. 「これは内部用のヘルパー」という意図が伝わりにくい

- **ヘルパー**＝他のメソッド（ここでは methodA / methodB）の仕事を手伝うための、補助的な処理。
- **内部用**＝インターフェースの「中」の実装の都合で使うだけで、**外（実装クラスや利用者）には見せたくない**もの。

デフォルトメソッドとして `commonLogic()` を書くと、

- インターフェース上は methodA / methodB と **同じ扱い**（どれも「この型が持つメソッド」）になる  
→ 「commonLogic は内部用のヘルパーだから、実装クラスからは呼ばないで」という意図が**コード上では伝わらない**。
- コメントで「内部用です」と書くことはできるが、**言語のルールでは「内部用」という区別がない**ので、うっかり呼ばれやすい。

つまり、  
**「内部用のヘルパー」という意図が、仕組みとして伝わりにくい**＝実装クラスの人から見ると「普通に使えるメソッド」にしか見えない、という説明です。

#### 3. インターフェースの「契約」としてのメソッドが増えてしまう

- **インターフェースの「契約」**＝  
  「この型を実装したクラスは、少なくとも **こういうメソッド（振る舞い）を提供する」** という約束。  
  通常、それは「外から使ってほしい機能」の一覧だと考えます。

- デフォルトメソッドは **その契約の一部** です。  
  → `commonLogic()` をデフォルトメソッドにすると、  
  **「このインターフェースは methodA / methodB に加えて、commonLogic も提供する」** という契約が増えたことになる。

- 本来の契約は「methodA と methodB が使えること」だけで、  
  **commonLogic は「契約」ではなく「実装の都合で使っている内部の処理」** にしたい。
- なのにデフォルトメソッドにしてしまうと、  
  **「契約」（外に約束するメソッド）が、意図せず増えてしまう**、という意味です。

#### まとめ（初学者向け）

| 表現 | 意味（かみ砕くと） |
|------|-------------------|
| **実装クラスから commonLogic() を呼べてしまう** | 「中でだけ使いたい」共通処理が、デフォルトメソッドだと外からも普通に呼べるので、実装クラスがそれを直接使えてしまう。 |
| **「内部用のヘルパー」という意図が伝わりにくい** | コード上は methodA と同じ「公開メソッド」に見えるので、「これは中だけで使う補助処理だから呼ばないで」という意図が伝わりにくい。 |
| **インターフェースの「契約」としてのメソッドが増える** | 契約＝「この型が外に提供するメソッド」なので、commonLogic をデフォルトにすると「提供するメソッド」が1つ増え、本来は内部の都合だけのものが契約に入ってしまう。 |

そのため、**共通処理は private メソッドにまとめる**と、

- 実装クラスからは呼べない（1を防げる）
- 「内部用」であることがコードで明確になる（2が解消する）
- 契約は methodA / methodB のままにできる（3を防げる）

という説明になります。
